# v0.9.0 Kyber-768 Post-Quantum Encryption Iteration Plan

> Feature branch: `feature/kyber-768-pqc-encryption`
> Created: 2026-06-22
> Target version: v0.9.0
> Status: Planning
> Primary goal: Add a user-facing post-quantum hybrid encryption key option backed by GnuPG composite Kyber+ECC support.

## 1. Executive Summary

Moaiy already ships a bundled GnuPG 2.5.18 binary. Local verification confirms that this binary reports Kyber as a supported public-key algorithm and can generate a `pqc` key with a Kyber-768 encryption subkey:

```text
gpg (GnuPG) 2.5.18
Pubkey: RSA, Kyber, ELG, DSA, ECDH, ECDSA, EDDSA
ssb:u:768:8:...::::::e:::+::ky768_bp256:8 23:
```

This iteration should expose that capability as a conservative, clearly labeled key type:

```text
Post-Quantum Hybrid (ML-KEM-768)
```

The implementation should not introduce a standalone cryptographic implementation. It should use GnuPG's existing OpenPGP/LibrePGP command surface and keep all sensitive operations in the current `GPGService` boundary.

## 2. Algorithm Decision

### Recommended Algorithm

Use GnuPG's composite Kyber+ECC key generation through:

```bash
gpg --quick-gen-key "Name <email>" pqc default never
```

Observed generated encryption subkey:

```text
ky768_bp256
```

Product-facing name:

```text
Post-Quantum Hybrid (ML-KEM-768)
```

Technical name:

```text
Composite Kyber-768 + ECC OpenPGP encryption key
```

Security boundary:

```text
Post-quantum protection applies to encryption key encapsulation. Signing, certification, authentication, and user ID binding remain classical ECC in the GnuPG composite key produced by `pqc`.
```

### Rationale

- It matches the bundled GnuPG capability that is already present in the app.
- It avoids custom cryptographic code in Swift.
- ML-KEM is standardized by NIST FIPS 203, and ML-KEM-768 is the middle parameter set with a practical balance of security and performance.
- GnuPG 2.5.1 release notes state that composite Kyber+ECC public key algorithms use the final FIPS 203 and LibrePGP specifications.
- The feature aligns with Moaiy's main encryption workflows. ML-DSA/Dilithium is a signature algorithm family and should not be the first PQC feature for a file/text encryption product.

References:

- NIST FIPS 203: https://csrc.nist.gov/pubs/fips/203/final
- GnuPG 2.5.1 release notes: https://dev.gnupg.org/T7191
- GnuPG downloads, current stable tracking: https://www.gnupg.org/download/index.html

## 3. Scope

### In Scope

- Add a new key type for post-quantum hybrid encryption.
- Generate PQC keys through GnuPG's `--quick-gen-key` path.
- Detect and display Kyber/PQC keys in key lists, detail views, filters, and statistics.
- Add localized UI strings in English and Simplified Chinese.
- Add unit tests for command building, parsing, display naming, and selection logic.
- Add integration tests that use the bundled GPG when available.
- Add backup, restore, and external `GNUPGHOME` migration regression coverage for keyrings containing PQC keys.
- Add release notes and user-facing compatibility guidance.

### Out of Scope

- Implementing Kyber/ML-KEM directly in Swift.
- Adding ML-DSA/Dilithium signature keys.
- Changing existing RSA/ECC defaults for all users.
- Migrating existing keys to PQC automatically.
- Uploading PQC keys to public keyservers by default.
- Claiming universal OpenPGP compatibility.
- Replacing current encryption, decryption, signing, or trust semantics.

## 4. Product Positioning

### Default Behavior

Keep the current default key type unchanged for this version. The PQC option should be available but not silently applied as the default until compatibility data is stronger.

Recommended first-release placement:

- Settings: allow `Post-Quantum Hybrid (ML-KEM-768)` as a default key type option.
- Create Key: add an explicit key type picker that defaults to the Settings value.
- Optional advanced affordance: add a compatibility note near the key type setting rather than in the main create-key form.

### User-Facing Wording

Use plain language and avoid exposing users to unnecessary algorithm internals:

- Short label: `Post-Quantum Hybrid`
- Detail label: `ML-KEM-768`
- Compatibility note: `Recipients need compatible GnuPG or LibrePGP software to use this key.`

The app must not say:

- `Quantum-proof`
- `Unbreakable`
- `Military-grade post-quantum`
- `Works with all OpenPGP apps`

## 5. Technical Architecture

### Current Key Generation Path

Current `GPGService.generateKey` builds a batch parameter file and runs:

```bash
gpg --batch --gen-key --status-fd 1
```

Local validation shows that this does not accept:

```text
Key-Type: pqc
```

It fails with:

```text
invalid algorithm
```

Therefore, the PQC implementation needs a dedicated generation path.

### Proposed Service Design

Add a new `KeyType` case:

```swift
case postQuantumHybrid = "Post-Quantum Hybrid"
```

Add key type capabilities instead of spreading conditionals:

```swift
var generationMode: KeyGenerationMode
var localizedDisplayKey: String
var compatibilityLevel: KeyCompatibilityLevel
```

Suggested internal types:

```swift
enum KeyGenerationMode {
    case batch
    case quick
}

enum KeyCompatibilityLevel {
    case broad
    case modern
    case experimentalInterop
}
```

Add a typed settings wrapper before adding the new persisted value. The current app stores `defaultKeyType` as an `Int` used by Settings, Create Key, and Pro team policy templates. Keep existing values stable:

```text
0 = RSA-4096
1 = RSA-2048
2 = ECC Curve25519
3 = Post-Quantum Hybrid
```

The wrapper should be the only place that maps persisted values to `KeyType`, localized display keys, and availability. Unknown or unsupported values must resolve to RSA-4096 for display and settings recovery, but attempted PQC generation must still fail closed when capability detection is negative.

Team policy template handling must be updated in the same phase:

- decode `defaultKeyType: 3`
- display the PQC localized name
- apply returned `policy.applied.defaultKeyType = 3`
- ignore or reject managed PQC defaults when runtime capability detection is negative
- keep older Pro modules that only return `0...2` working without migration

Add a PQC-specific private method in `GPGService`:

```swift
private func generatePostQuantumHybridKey(
    name: String,
    email: String,
    passphrase: String?
) async throws -> String
```

Use command arguments shaped like:

```swift
[
    "--batch",
    "--pinentry-mode", "loopback",
    "--passphrase-fd", "0",
    "--status-fd", "1",
    "--quick-gen-key",
    "\(name) <\(email)>",
    "pqc",
    "default",
    "never"
]
```

All options must appear before `--quick-gen-key` and its positional arguments. Local validation shows that putting `--status-fd` after `never` causes GnuPG to treat it as a positional argument and fail with:

```text
gpg: Note: '--status-fd' is not considered an option
usage: gpg [options] --quick-generate-key USER-ID [ALGO [USAGE [EXPIRE]]]
```

Passphrases must be sent over stdin with `--passphrase-fd 0`, matching the existing subkey-management pattern. Do not pass real passphrases through `--passphrase`, because command-line arguments can be visible to process inspection. Local validation confirms that `--quick-gen-key ... pqc default never` works with `--passphrase-fd 0` for both empty and non-empty passphrases.

### Command Builder Boundary

The project already has `GPGCommandBuilder`. Add PQC command construction there if the current architecture supports generation commands cleanly. If not, keep the first implementation private to `GPGService` and add tests around the service behavior. Do not create a broad abstraction until there are at least two quick-generation command paths.

### Key Parsing

Update parsing and display normalization for:

- `Kyber`
- `ky768_bp256`
- algorithm id `8` in GnuPG colon output
- primary key plus encryption subkey layout produced by `pqc`

PQC display must be derived from the encryption-capable subkey, not only the primary key. GnuPG `pqc` generation creates a classical ECC primary key and a Kyber encryption subkey. Local output can look like:

```text
sec:u:384:19:...:::u:::scESC:::+::brainpoolP384r1:23::0:
ssb:u:768:8:...::::::e:::+::ky768_bp256:8 23:
```

If the UI only uses the primary key record, it may incorrectly display the key as `brainpoolP384r1` or `ECC-384`. The normalized key summary should inspect subkeys and classify the key as post-quantum hybrid when an encryption-capable subkey has a Kyber token such as `ky768_bp256` or GnuPG public-key algorithm id `8`.

Current `parseKeyList` intentionally ignores most `sub`/`ssb` records for key-level operations. This iteration must add an explicit key-summary model rather than overloading the primary `algorithm` field. Suggested additions:

```swift
struct GPGKeyAlgorithmSummary: Hashable {
    let primaryAlgorithm: String
    let primaryKeyLength: Int
    let encryptionAlgorithms: [String]
    let displayNameKey: String
    let shortDisplayNameKey: String
    let isPostQuantumHybrid: Bool
}
```

`GPGKey` should keep the existing `algorithm` and `keyLength` values for compatibility, while cards, filters, and statistics move to the summary display values. This avoids breaking existing tests and code paths that expect primary-key metadata.

Expected user display:

```text
Post-Quantum Hybrid
ML-KEM-768
```

Expected technical display where needed:

```text
Kyber-768 + ECC
```

### Capability Detection

Add runtime detection before showing or using the PQC option:

```bash
gpg --with-colons --list-config
```

Require:

```text
cfg:pubkeyname:...;Kyber;...
```

If unavailable:

- Hide the option from settings and creation flows, or disable it with a localized explanation.
- Keep existing RSA/ECC flows unaffected.
- Record a non-sensitive diagnostic event in logs.
- Fail closed if a user tries to create a PQC key while capability detection is unavailable or negative. Do not silently generate RSA or ECC instead, because that would violate the user's security intent.

### Bundled GPG Version Policy

Current bundled version:

```text
GnuPG 2.5.18
libgcrypt 1.12.1
```

Official GnuPG download page currently lists GnuPG 2.5.20 as stable. This iteration should include a decision gate:

1. First land PQC support against the existing bundled 2.5.18 because it is already validated locally.
2. Separately evaluate whether the bundle should be upgraded to 2.5.20 before release.
3. Only upgrade the bundle in this branch if it fixes a PQC bug, security issue, packaging issue, or App Store compatibility concern.

## 6. UI and UX Plan

### Settings

Update `SettingsView` default key type picker:

- Add `Post-Quantum Hybrid (ML-KEM-768)` as an option when capability detection passes.
- Keep persisted `defaultKeyType` values stable through the typed wrapper described above.
- Avoid breaking existing values:
  - `0`: RSA-4096
  - `1`: RSA-2048
  - `2`: ECC
  - `3`: PQC hybrid

Do not add the long PQC label to the existing segmented control without layout changes. The current Settings UI uses a constrained segmented picker, and a fourth long item will likely truncate or crowd the row. Recommended UI:

- Use a `.menu` picker for default key type, or
- Keep the existing segmented picker for RSA/ECC and place PQC in a compact advanced menu.

The preferred first implementation is a single `.menu` picker with short labels and a caption shown below the row when PQC is selected or unavailable.

### Create Key Flow

Current `CreateKeyView` only displays the selected default key type. For this iteration:

- Add an explicit key type picker in its own Form section, defaulting to the user's Settings value.
- Use a `.menu` picker, not a segmented control, to avoid horizontal overflow in the modal.
- Keep the flow compact and avoid exposing algorithm internals beyond the localized label and compatibility note.
- Display a one-line caption only when PQC is selected or unavailable.
- If PQC is selected and capability detection fails, stop key generation and show a localized, friendly error. Do not fall back to RSA-4096 or ECC automatically.
- Keep empty-passphrase warning behavior unchanged.
- Verify the modal at its current adaptive size. Text must not overlap the footer or push the passphrase tips into an awkward scroll state.

### Key Cards and Detail Views

Update badges and metadata:

- Show a compact card label such as `PQC Hybrid` or `ML-KEM-768` instead of raw `8-768` or `Kyber-768`.
- Use an existing symbol such as `shield.lefthalf.filled` or `lock.shield`.
- Use a distinct but restrained badge color that does not overpromise security.
- Keep long explanatory text out of `KeyCardView`; the card has a right-side drop zone and action menu. Place the full `Post-Quantum Hybrid (ML-KEM-768)` label and encryption-only note in details, export/import prompts, or tooltips.

Algorithm filter and statistics should use normalized display names from `GPGKeyAlgorithmSummary`, not raw primary `algorithm` values. Existing RSA/ECC grouping must remain stable.

### Subkey Governance

PQC keys need explicit behavior in the subkey management sheet:

- `listSubkeys` should map public-key algorithm id `8` and tokens such as `ky768_bp256` to a localized Kyber/ML-KEM display.
- Updating expiration, disabling, enabling, and revoking existing PQC encryption subkeys should be supported if current GnuPG commands already work.
- Adding a new encryption subkey to a PQC primary key must not silently create a classical `cv25519` encryption subkey and present it as PQC.
- For v0.9.0, disable "add encryption subkey" for PQC hybrid keys unless a verified Kyber quick-add command exists. Signing and authentication subkey additions may remain classical ECC, with a clear localized note.
- Add tests for subkey display and add-subkey gating.

### Warnings and Compatibility

Add compatibility messaging in places where users may share public keys:

- Export public key
- Upload to keyserver
- Import result summary
- Key detail metadata

Message should be concise:

```text
Some older OpenPGP apps may not support this key type.
```

Add an additional short note wherever the app describes the security properties:

```text
Post-quantum protection applies to encryption. Signatures still use classical ECC.
```

## 8. Security Plan

### Security Invariants

- No custom cryptographic implementation.
- No sensitive material in logs.
- No passphrase exposure in diagnostics, errors, or test output.
- Preserve app sandbox compatibility.
- Preserve the current `GNUPGHOME` isolation model.
- Preserve timeout and cancellation handling for key generation.

### Passphrase Handling

Confirm the safest loopback behavior for `--quick-gen-key`:

- passphrase present: use `--pinentry-mode loopback --passphrase-fd 0` and pass the value through stdin
- passphrase absent: use the same `--passphrase-fd 0` path with a single newline on stdin, matching local validation
- avoid shell invocation; pass arguments through `Process`
- avoid logging command input, because it may contain a passphrase

### Compatibility Safety

PQC keys should not become the silent default until:

- import/export works in Moaiy
- encrypt/decrypt round trips work locally
- unsupported recipient errors are friendly
- keyserver behavior is verified
- external compatibility matrix is documented
- backup, restore, and external keyring migration behavior is verified

### Algorithm Claim Boundary

All product copy, release notes, and help text must describe this feature as post-quantum hybrid encryption support. The implementation must not imply that signatures, identity certifications, trust signatures, or authentication are post-quantum protected.

## 9. Testing Strategy

### Unit Tests

Add or update tests for:

- `KeyType` metadata for PQC hybrid
- settings value mapping
- selected default key type resolution
- GPG capability detection parser
- GPG colon output parsing for `Kyber`, `ky768_bp256`, and algorithm id `8`
- display naming for PQC primary and subkey records
- user-facing error mapping for unsupported PQC
- command argument construction without leaking passphrases
- command argument ordering for `--quick-gen-key`
- fail-closed behavior when PQC is selected but unsupported
- key summary classification derived from Kyber encryption subkeys
- typed default key setting mapping, including unknown values and Pro policy value `3`
- key card/filter/statistics display using algorithm summary instead of raw primary algorithm
- subkey algorithm display and add-subkey gating for PQC hybrid keys

### Integration Tests

Use isolated `GNUPGHOME` directories.

Current public `GPGService.shared.generateKey` uses the active app keyring. Before adding PQC integration tests, add a test seam that can run GPG commands against a temporary home without touching the developer's or CI runner's real keyring. Acceptable approaches:

- initialize a test-only `GPGService` with an injected `GNUPGHOME`
- add a scoped test helper that passes `gpgHome` through the process executor
- run integration command tests through a dedicated lower-level executor wrapper

Do not rely on `~/.gnupg` or the app's live container for PQC integration tests.

Required tests:

1. Generate PQC key with no passphrase.
2. Generate PQC key with passphrase.
3. List generated key and detect Kyber encryption subkey.
4. Export and re-import public key.
5. Export and re-import secret key with passphrase when applicable.
6. Encrypt text/file to PQC recipient.
7. Decrypt text/file with PQC secret key.
8. Verify existing RSA/ECC generation still passes.
9. Verify unsupported GPG capability handling with a mock or system override.
10. Back up and restore a PQC keyring.
11. Migrate a keyring containing PQC keys from an external `GNUPGHOME`.
12. Verify restored or migrated PQC keys still display as post-quantum hybrid and can decrypt previously encrypted content.
13. Verify Pro team policy template value `3` maps to PQC only when supported and remains recoverable when unsupported.
14. Verify subkey governance does not silently add a classical encryption subkey to a PQC hybrid key.

### Manual QA

Run on macOS 12+ target environment:

- Fresh install with no existing keyring.
- Existing user keyring with RSA/ECC keys.
- Create PQC key through Settings-selected default.
- Create PQC key through the create-key key type picker.
- Export public key and inspect armored output.
- Import exported PQC public key into a second isolated keyring.
- Encrypt from one keyring to the PQC recipient.
- Decrypt in the original keyring.
- Back up a keyring containing a PQC key and restore it into a clean app container.
- Migrate a keyring containing a PQC key from an external GnuPG home.
- Try importing the PQC key into older GnuPG 2.4.x and document expected failure or degraded behavior.
- Test app sandbox build, code signing, and notarization path if bundle changes.

## 12. Risk Register

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Older OpenPGP clients cannot use PQC keys | Users may share unusable keys | Label as compatibility-limited and keep default unchanged |
| `--quick-gen-key` passphrase behavior differs from batch generation | Unprotected or inaccessible keys | Add explicit passphrase integration tests |
| Keyserver support is inconsistent | Public key publishing may fail or confuse users | Add warning before upload and document behavior |
| GnuPG 2.5.x PQC behavior changes | Regression across bundled upgrades | Add capability and generation integration tests |
| Raw algorithm parsing displays poor labels | User confusion | Normalize Kyber/PQC display centrally |
| App Store review questions crypto claims | Release delay | Avoid overclaims and document GnuPG/OpenPGP basis |
| GnuPG options are appended after `--quick-gen-key` positionals | Key generation fails at runtime | Keep all GnuPG options before `--quick-gen-key` and add command ordering tests |
| Passphrases are passed in argv | Sensitive data may be visible to process inspection | Use `--passphrase-fd 0` and stdin, matching existing subkey operations |
| PQC fallback silently creates RSA/ECC keys | User receives weaker-than-requested key material | Fail closed and require explicit user selection |
| PQC classification only reads the primary key | PQC keys display as ECC and become hard to find | Classify from encryption-capable subkeys |
| Backup or migration drops PQC metadata | Restored keys work but appear as non-PQC | Add backup, restore, migration, and display regression tests |
| Long PQC labels break Settings, Create Key, or Key Card layout | Poor UX and text truncation | Use menu pickers, compact card labels, and localized layout checks |
| Pro team policy default key type mapping stays integer-only and incomplete | Managed defaults may resolve to the wrong key type | Add a typed wrapper and update policy value `3` handling |
| Subkey add flow creates classical encryption subkeys on PQC keys | Users may believe added encryption subkeys are PQC | Gate add-encryption-subkey behavior for PQC keys until Kyber quick-add is verified |
| Integration tests use the live keyring | Developer or CI keyrings may be polluted | Add an injected temporary `GNUPGHOME` test seam before integration tests |
