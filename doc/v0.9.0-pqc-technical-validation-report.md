# v0.9.0 PQC Technical Validation Report

> Date: 2026-06-23
> Branch: `feature/kyber-768-pqc-encryption`
> Scope: Pre-implementation validation for the first four Kyber-768 iteration risks.
> Tooling: Bundled `Moaiy/Resources/gpg.bundle/bin/gpg`

## 1. Summary

The first four pre-implementation validation items are technically feasible with the bundled GnuPG 2.5.18 binary:

- PQC key generation works through `--quick-gen-key ... pqc default never`.
- Kyber capability detection works through `--with-colons --list-config`.
- GnuPG colon output provides stable signals for PQC classification.
- PQC public-key export/import and file encryption/decryption work end to end.

One important implementation risk was found outside the narrow encrypt/decrypt path: importing exported PQC secret keys into a fresh temporary home failed in direct shell validation with agent-related errors. Moaiy's implementation must treat PQC secret-key restore/import as a dedicated validation area before release, even though public-key import and normal local decryption work.

## 2. Environment

Validated bundled GPG:

```text
gpg (GnuPG) 2.5.18
```

All validation keyrings used temporary `GNUPGHOME` directories. No project or user keyring was intentionally used.

## 3. Validation Results

### 3.1 PQC Generation Command

Validated command shape:

```bash
gpg \
  --batch \
  --pinentry-mode loopback \
  --passphrase-fd 0 \
  --status-fd 1 \
  --quick-gen-key "Moaiy PQC Empty <pqc-empty@example.invalid>" \
  pqc default never
```

Result:

```text
[GNUPG:] KEY_CREATED B 6C907427B0A24BA7713C503248ABB8D81F1F6F7E
```

The same command shape also worked with a non-empty passphrase supplied through stdin:

```text
[GNUPG:] KEY_CREATED B D176186FAD300A371991116ED6E3E324B06C5CC7
```

Negative command ordering was also validated. Placing `--status-fd 1` after `pqc default never` fails:

```text
bad-order-exit=2
gpg: Note: '--status-fd' is not considered an option
usage: gpg [options] --quick-generate-key USER-ID [ALGO [USAGE [EXPIRE]]]
```

Solution:

- Implement a dedicated PQC generation path.
- Place all GPG options before `--quick-gen-key`.
- Use `--passphrase-fd 0` and stdin for both empty and non-empty passphrases.
- Parse `KEY_CREATED` from status output as the primary success signal.
- Keep the existing fingerprint-delta fallback as a secondary recovery path.

### 3.2 Capability Detection

Validated command:

```bash
gpg --with-colons --list-config
```

Relevant output:

```text
cfg:version:2.5.18
cfg:pubkey:1;8;16;17;18;19;22
cfg:pubkeyname:RSA;Kyber;ELG;DSA;ECDH;ECDSA;EDDSA
```

Result:

```text
capability=kyber-present
```

Solution:

- Add `GPGCapability` parsing for `cfg:pubkeyname` and `cfg:pubkey`.
- Treat either `Kyber` in `cfg:pubkeyname` or algorithm id `8` in `cfg:pubkey` as positive Kyber capability.
- Cache the result after GPG readiness.
- If unavailable, hide or disable PQC UI and fail closed on attempted PQC generation.
- Add parser fixtures for:
  - Kyber present by name
  - Kyber present by algorithm id
  - Kyber missing
  - empty or malformed config output

### 3.3 Key Parsing and Display Assumptions

Generated PQC keys have a classical ECC primary key and a Kyber encryption subkey.

Observed secret key output:

```text
sec:u:384:19:48ABB8D81F1F6F7E:1782183109:::u:::scESC:::+::brainpoolP384r1:23::0:
fpr:::::::::6C907427B0A24BA7713C503248ABB8D81F1F6F7E:
uid:u::::1782183109::...::Moaiy PQC Empty <pqc-empty@example.invalid>::::::::::0:
ssb:u:768:8:FAF4A4B609E6DEF9:1782183109::::::e:::+::ky768_bp256:8 23:
fpr:::::::::FAF4A4B609E6DEF917CF65F99E90C6DD03A33A569F2FDC0AA25E0312DB650D5F:
```

Observed public key output after import into a separate sender keyring:

```text
pub:-:384:19:DB0ABFD5D9C9B529:1782183111:::-:::scESC:::::brainpoolP384r1:23::0:
fpr:::::::::7C41B8B68889D5E41A072B3ADB0ABFD5D9C9B529:
uid:-::::1782183111::...::Moaiy PQC Recipient <pqc-recipient@example.invalid>::::::::::0:
sub:-:768:8:B177263F3E55ADD2:1782183111::::::e:::::ky768_bp256:8 23:
fpr:::::::::B177263F3E55ADD2B6A8EE73B957B98578263F56B5F5D3A95C9ACA9BC5CAA38E:
```

Classification signals:

- Primary algorithm id: `19`
- Primary curve token: `brainpoolP384r1`
- Encryption subkey algorithm id: `8`
- Encryption subkey token: `ky768_bp256`
- Encryption usage: `e`
- Subkey length field: `768`

Solution:

- Do not classify PQC keys from the primary key record.
- Preserve current `GPGKey.algorithm` and `GPGKey.keyLength` compatibility semantics.
- Add a derived `GPGKeyAlgorithmSummary` that captures primary metadata and encryption subkey capabilities.
- Update key cards, algorithm filters, and statistics to use the summary display value.
- Add parser tests for both `sub` and `ssb` records containing algorithm id `8` and token `ky768_bp256`.
- Map subkey algorithm id `8` to a localized Kyber/ML-KEM display name.

Recommended model:

```swift
struct GPGKeyAlgorithmSummary: Hashable {
    let primaryAlgorithm: String
    let primaryKeyLength: Int
    let encryptionAlgorithms: [String]
    let displayNameKey: String
    let shortDisplayNameKey: String
    let isPostQuantumHybrid: Bool
}
```

### 3.4 End-to-End Encryption and Decryption

Validated flow:

1. Generate PQC recipient key in a temporary recipient home.
2. Export recipient public key.
3. Import recipient public key into a separate temporary sender home.
4. Encrypt a plaintext file to the PQC recipient with `--trust-model always`.
5. Decrypt the ciphertext in the recipient home.

Result:

```text
e2e=success
```

Decryption stderr confirms Kyber was used:

```text
gpg: encrypted with ky768_bp256 key, ID B177263F3E55ADD2, created 2026-06-23
      "Moaiy PQC Recipient <pqc-recipient@example.invalid>"
```

Passphrase-protected PQC key behavior was also validated:

```text
wrong_decrypt_exit=2
correct_decrypt_exit=0
passphrase-e2e=success
```

Solution:

- Existing file encryption/decryption paths should work for PQC recipients once the recipient key exists and trust handling is satisfied.
- Continue requiring current trust override behavior for imported public keys.
- Add integration tests for:
  - local unprotected PQC decrypt
  - passphrase-protected PQC decrypt
  - wrong passphrase failure mapping
  - public-key import followed by encryption from a separate temporary home

## 4. Additional Finding: Secret-Key Restore Risk

Public-key import worked:

```text
gpg: key DB0ABFD5D9C9B529: public key "Moaiy PQC Recipient <pqc-recipient@example.invalid>" imported
gpg: Total number processed: 1
gpg:               imported: 1
```

However, importing an exported PQC secret key into a fresh temporary home failed in direct shell validation:

```text
public_import_exit=0
secret_import_exit=2
decrypt_exit=2
restore2-decrypt=failure
```

Observed error:

```text
gpg: key DB0ABFD5D9C9B529/B177263F3E55ADD2: error sending to agent: IPC parameter error
gpg: error reading 'recipient-secret.asc': IPC parameter error
gpg: import from 'recipient-secret.asc' failed: IPC parameter error
gpg:       secret keys read: 1
```

Secret-first import attempts also failed when the temporary home had no reachable agent:

```text
gpg: error getting the KEK: No agent running
gpg: import from 'recipient-secret.asc' failed: No agent running
```

This does not block PQC generation or normal local encryption/decryption, but it is a release-blocking backup/restore risk until resolved.

Solution:

- Add a dedicated backup/restore validation spike before marking Phase 5 complete.
- Reproduce through Moaiy's actual `GPGService.importKey` path, not only shell commands.
- Ensure the app launches and verifies `gpg-agent` before PQC secret import.
- Confirm whether imported PQC secret keys require a different import flag, agent environment, or GnuPG bundle adjustment.
- Add an automated restore test that imports exported PQC secret material into a temporary home and decrypts a previously encrypted message.
- Do not claim PQC backup/restore support until this test passes.

## 5. Implementation Recommendations

### Generation

Implement a separate private method:

```swift
private func generatePostQuantumHybridKey(
    name: String,
    email: String,
    passphrase: String?
) async throws -> String
```

Use arguments:

```swift
[
    "--batch",
    "--pinentry-mode", "loopback",
    "--passphrase-fd", "0",
    "--status-fd", "1",
    "--quick-gen-key",
    userID,
    "pqc",
    "default",
    "never"
]
```

Input:

```swift
(passphrase ?? "") + "\n"
```

### Capability Gate

Add:

```swift
struct GPGCapabilities {
    let supportsKyber: Bool
}
```

Expose it through `GPGService` after readiness. UI should read this state before offering PQC.

### Test Isolation

Before adding integration tests, add a test seam for temporary homes:

- a test-only initializer for `GPGService`, or
- a lower-level command runner that accepts `gpgHome`, or
- a scoped helper around `GPGProcessExecutor`.

Do not run PQC integration tests against `~/.gnupg` or the app's live container.

### Parser Work

Add parsing support for subkey-level algorithm metadata in `parseKeyList`, then derive `GPGKeyAlgorithmSummary`.

The minimum PQC rule:

```text
isPostQuantumHybrid = any encryption-capable subkey has algorithm id 8 or token ky768_bp256
```

### Restore Work

Treat secret-key restore as separate from public-key import and encryption. The validation results show the happy path for local use works, but exported secret-key restore needs more work around agent availability and import behavior.

## 6. Go / No-Go

Go for implementation of:

- PQC capability detection
- typed key type mapping
- PQC key generation
- PQC parser summary
- public-key import and encryption/decryption flow

No-go until resolved:

- declaring PQC backup/restore complete
- release notes claiming PQC secret-key restore support
- enabling any backup/restore acceptance gate without a passing PQC secret import test
