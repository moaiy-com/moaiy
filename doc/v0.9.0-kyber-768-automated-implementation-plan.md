# v0.9.0 Kyber-768 Automated Implementation Plan

> Created: 2026-07-06
> Branch: `feature/kyber-768-pqc-encryption`
> Scope: Automation-ready implementation runbook for v0.9.0 Kyber-768 support.
> Source plan: `doc/v0.9.0-kyber-768-pqc-iteration-plan.md`
> Validation source: `doc/v0.9.0-pqc-technical-validation-report.md`

## 1. Purpose

This document converts the v0.9.0 Kyber-768 iteration plan into an execution plan that an agent or CI runner can follow without product clarification during implementation.

The plan is intentionally fail-fast:

- Every phase has concrete file targets.
- Every phase has automated verification commands.
- Manual QA is moved after automated acceptance, not inside core implementation.
- Release claims stay blocked until backup and restore coverage passes for PQC secret keys.

## 2. Plan Review Findings

### P1 Findings

1. The source plan still references bundled GnuPG 2.5.18 as the current baseline. The repository has already upgraded `Moaiy/Resources/gpg.bundle` to GnuPG 2.5.20. All implementation and test gates must use 2.5.20 as the baseline.

2. The secret-key restore risk appears too late in the original phase sequence. It must be moved before UI completion and release notes, because a failed PQC secret restore changes the supported feature claim.

3. Integration tests need an isolated `GNUPGHOME` seam before PQC generation tests are added. Current `GPGService.shared` uses the app-managed keyring and several integration tests exercise shared state. PQC tests must not depend on the developer keyring or app container.

4. `defaultKeyType` is duplicated across `SettingsView`, `CreateKeyView`, Pro team policy template parsing, and tests. Adding value `3` directly in views would create drift. A typed mapping layer must land before UI changes.

5. PQC classification must not use the primary key record alone. GnuPG `pqc` produces an ECC primary key and a Kyber encryption subkey. Parsing must classify the whole key from encryption-capable subkeys.

6. The existing `Moaiy` scheme is not configured for the Xcode test action. Automated test commands must use `MoaiyTests`.

7. Xcode builds must not run concurrently against the same DerivedData directory. A previous verification hit `build.db` locking when build and test ran in parallel.

8. Localization automation currently checks 11 locales, not only English and Simplified Chinese. Any new String Catalog keys must be populated for all locales enforced by `scripts/check_localization.py`.

### P2 Findings

1. Current parser tests duplicate parsing helper logic instead of exercising one shared pure parser boundary. PQC parsing work should reduce that duplication where practical.

2. Settings currently uses a segmented picker for three key types. Adding a fourth long PQC label there is a layout risk. Use a menu picker before adding the new option.

3. Create Key currently only displays the selected default key type. It needs an explicit key type picker so users can create one PQC key without changing global settings.

4. Algorithm filters and statistics use `GPGKey.algorithm` directly. They should move to derived algorithm summary display to avoid showing raw `8`, `19`, or `brainpoolP384r1` for PQC keys.

5. Subkey governance must be gated. Adding a classical encryption subkey to a PQC hybrid key must not be presented as adding PQC encryption.

6. Release validation scripts should include PQC-specific tests after they exist. Full `xcodebuild test` remains the canonical local gate.

## 3. Execution Rules

Automation must follow these rules:

1. Stop on first failing gate.
2. Do not ask for user decisions during implementation. Use the defaults in this document.
3. Do not introduce custom cryptography.
4. Do not pass passphrases through command-line arguments.
5. Do not run PQC integration tests against `~/.gnupg` or a live app container.
6. Do not silently fall back from PQC to RSA or ECC.
7. Do not run two `xcodebuild` jobs with the same DerivedData path.
8. Keep `defaultKeyType` values stable:
   - `0`: RSA-4096
   - `1`: RSA-2048
   - `2`: ECC Curve25519
   - `3`: Post-Quantum Hybrid
9. Keep all code identifiers and comments in English.
10. Keep all user-facing text in `Localizable.xcstrings`.

## 8. Phase P2: GPG Capability Detection

### Objective

Detect whether the active bundled or debug GPG supports Kyber before UI or generation uses PQC.

### Implementation Steps

1. Add `GPGCapabilities`.
2. Add a parser for `gpg --with-colons --list-config`.
3. Treat either signal as Kyber support:
   - `cfg:pubkeyname` contains `Kyber`

4. Load capabilities after `verifyGPG()` and before `isReady = true`.
5. Expose capability state read-only to view models.
6. Cache the result for the active service instance.

### Implementation Steps

2. Use this exact option order:

```swift
[
    "--batch",
    "--pinentry-mode", "loopback",
    "--passphrase-fd", "0",
    "--status-fd", "1",
    "--quick-gen-key",
    userID,
    "pqc",
    "default",
    "never"
]
```

```swift
(passphrase ?? "") + "\n"
```

## 16. Definition of Done

The v0.9.0 implementation is done only when all items are true:

- Bundled GPG is 2.5.20 or newer within the approved 2.5.x stable line.
- Bundle verification has zero failures.
- Capability detection reports Kyber support for the bundled GPG.
- PQC generation works with empty and non-empty passphrases.
- PQC generated keys are displayed as post-quantum hybrid, not raw ECC primary keys.
- Existing RSA-4096, RSA-2048, and ECC generation still work.
- Text and file encryption/decryption round trips pass with PQC recipients.
- Public-key export/import works with PQC keys.
- Secret-key backup/restore works with PQC keys, or release claims explicitly exclude it.
- Settings uses a layout-safe picker.
- Create Key has an explicit key type picker.
- Pro template value `3` is handled safely.
- All new strings pass localization checks.
- `MoaiyTests` full suite passes.
- Release notes include compatibility caveats and the encryption-only claim boundary.

## 18. Rollback Strategy

If a phase fails and cannot be fixed quickly:

1. Stop implementation.
2. Keep previously passing commits.
3. Do not partially expose PQC UI.
4. Disable only the latest incomplete phase behind capability and feature gates.
5. Re-run the previous phase gate.

Rollback must never change persisted values `0...2`, remove existing RSA/ECC behavior, or downgrade the bundled GPG without a separate explicit decision.

## 19. Release Notes Requirements

Release notes must include:

- `Post-Quantum Hybrid (ML-KEM-768)` key creation is available for compatible GnuPG/LibrePGP workflows.
- Post-quantum protection applies to encryption.
- Signatures, certifications, and trust remain classical ECC in the generated composite key.
- Some older OpenPGP applications may not support this key type.
- Existing RSA/ECC keys are unchanged.
- Backup and restore support status must match the P7 result exactly.

Do not use:

- `quantum-proof`
- `unbreakable`
- `military-grade post-quantum`
- `compatible with all OpenPGP apps`
